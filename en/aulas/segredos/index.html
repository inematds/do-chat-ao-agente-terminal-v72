Lesson 5 · 14 min

Secrets don't go in the text

A key pasted into a document, a screenshot, or a request becomes access for whoever reads it, and it stays valid after the conversation ends. Keeping the secret separate from everything else, before the first saved version, lets you share the folder without worry.

Start the lesson

In this lesson you will

  1. 1.env holds the key; .env.example shows only the names
  2. 2.gitignore written before the first version
  3. 3Leaked? Change the key at the source first
  4. 4The AI needs the variable name, not the value

Goal: create .env, .env.example and .gitignore before the first commit, and know what to do if a key leaks.

1/5

.env

It stores variables: a name, an equals sign and a value. It's not a safe: it isn't encrypted, and anyone who opens the file can read it. That's why it stays only on your machine and never goes to Git.

Scroll the page: each step below lights up its part of the diagram.

  1. 1/5

    .env

    It stores variables: a name, an equals sign and a value. It's not a safe: it isn't encrypted, and anyone who opens the file can read it. That's why it stays only on your machine and never goes to Git.

  2. 2/5

    .env.example

    The same names, with fake values. Whoever receives the project sees what needs to be filled in, but doesn't get access to anything. Remember: the one that ends in example is the example.

  3. 3/5

    .gitignore

    Each line is a pattern. .env catches the file; .env.* catches variants like .env.local; the line with ! opens an exception and puts the .env.example back on the list of what is kept.

  4. 4/5

    History

    .gitignore only applies to what Git hasn't stored yet. If the .env already went into a commit, a line written afterward doesn't take it out of the history. That's why the list comes before the first version.

  5. 5/5

    Ignore before the first commit

    The .env with the real value stays at home, the .env.example circulates, and the .gitignore decides that before Git stores any version. Once the mail pouch has left, crossing the paper off the list doesn't bring it back.

In the AGENTS.md rule: "Never write keys or passwords in a text file; they stay in the .env."

02 · Four rules about secrets

Click on each one.

1. A credential is the room key

A password, an API key and a bot token let whoever has them act on behalf of your account, and you're the one who pays.

Before sending a screenshot, check the corners of the screen: a visible password becomes everyone's who received it.

Corrected screenshotThe same screen, with the password covered before sending.

2. The AI needs the name

To help, the AI almost always only needs to know the variable exists, such as TELEGRAM_BOT_TOKEN.

A real value doesn't go in a request, a course example or a file sent to the AI unless necessary.

The right requestThe bot token is in the TELEGRAM_BOT_TOKEN variable in the .env.

3. The list before the version

Create the .gitignore before the first git commit. It does not remove from the history what has already gone in.

In the next lesson, git status is the proof: the .env must not appear.

Checkgit status does not show the .env.

4. Did it leak?

If a key was published or pasted by mistake, the first fix is to revoke the key on the site that created it and generate another one. Deleting the message or the line does not invalidate the copy someone has already seen.

Only after that, take care of the file and the history.

Order1. Revoke and replace. 2. Clean up the file.

03 · The three files

In the meu-primeiro-agente folder. The key is fake, for practice.

cmd · create the practice .env and the .gitignore
cd %USERPROFILE%\projetos\meu-primeiro-agente
echo MINHA_CHAVE=teste123> .env
echo MINHA_CHAVE=preencha_localmente> .env.example
echo .env> .gitignore
echo .env.*>> .gitignore
echo !.env.example>> .gitignore
type .gitignore
.gitignore (what it should contain)
.env
.env.*
!.env.example
AGENTS.md · new rule
- Never write keys or passwords in a text file; they stay in the .env.
- If you need a key, cite the variable name, never the value.
Simulation: illustrative example
C:\Users\ana\projetos\meu-primeiro-agente> type .gitignore
.env
.env.*
!.env.example

One > creates the file (or replaces its content); two >> add a line at the end.

  • Space before the >: echo .env > .gitignore writes ".env " with a trailing space. Write it attached: echo .env> .gitignore.
  • Key in AGENTS.md "so the agent knows how to use it": anything that is in text can end up on GitHub.
  • .gitignore after the commit: the .env is still in the old version.
